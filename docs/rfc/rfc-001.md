# RFC-001: ASSI — Foundry infrastructure lifecycle and custody

Revision: 2026-10-16. Status: accepted product boundary; implementation design
and operational qualification remain open. Core implementation language: Go.

## Purpose and ownership

ASSI brings order to infrastructure inside Foundry. It records what belongs to
each project, why it exists, its intended lifecycle, who can change it and the
allowed cost. It reconciles that intent with observed cloud, DNS and deployment
state and performs authorized changes through scoped protected executors.

Zati is the owner's organizational front door. The owner or an authorized Zati
workflow supplies intent; ASSI owns infrastructure desired-state enforcement.
Bora collects operational/cost evidence, flags drift and waste, and independently
checks outcomes. Foundry provides engineering delivery and operational controls.
A separate ASSI process or principal is appropriate security isolation, not a
separate administered product. Foundry remains usable without Zati.

This RFC supersedes the [original authored draft](../archive/20261016/rfc-001.md.source).
Its typed-catalog, reviewable IaC, policy, least-privilege, audit, recovery and
build-versus-reuse requirements survive. No implementation is claimed.

## Scope and non-goals

Infrastructure custody includes cloud resources, DNS, Kubernetes/Helm/GitOps
changes and other privileged deployment routes explicitly enrolled by scope.
A missing CLI in a sandbox is not an authorization boundary: agents must not
obtain ambient cloud write credentials or unrestricted deployment identities.
Application schema migration, package publication and business data changes are
separately scoped effects, not automatically ASSI-owned because they mutate state.

ASSI does not accept arbitrary shell, IaC programs or provider requests from a
model. Models cannot modify policy, broaden credentials or turn observations
into authorization. Existing protected CI/IaC controllers can execute on ASSI's
behalf, using narrowly delegated authority rather than one omnipotent global
identity. No single cross-service database or duplicate lifecycle scheduler is
required. Read-only diagnostics remain possible under their own project scopes.

## Resource registry and desired lifecycle

Each project/environment record contains stable identity, owner, repository,
intended state (`active`, `paused`, `retiring`, `retired`), permitted accounts,
regions, domains and clusters, deployment source/revision, expected resource
set, cost ceiling, expiry/review date and retention/recovery requirements.
Resource records bind provider identity and resource type to project/environment,
dependencies, IaC ownership, associated data, observed state/time, and evidence
of allocation or explicitly unresolved ownership. Tags are evidence, not proof.

Desired infrastructure definitions remain reviewable in Git/IaC. A durable
transactional operation store retains requests, policy decisions, approvals,
leases, attempts, uncertainty and provider receipts. A rebuild needs both
IaC/provider state and operation/authority history; Git alone cannot recover an
ambiguous write. PostgreSQL or another qualified transactional store may supply
that subsystem without permitting direct cross-service table access.

Inventory covers all explicitly authorized accounts and regions and reports
scan failures and unsupported resource families. Unattributed resources are
unknown, not automatically unused. Project retirement does not imply shared
resources, backup data or corporate domains are disposable. Cost reports
separate gross usage from credits, historic charges and verified future savings.

## Typed request and effect lifecycle

A bounded initial catalog can expose `list_resources`, `get_project_footprint`,
`preview_change`, `request_change`, `get_change_status`, `request_retirement`,
`get_retirement_status` and `request_capability`. Exact schemas and adapters are
design outputs; these names are not shipped MCP tools. Use the official MCP SDK;
HTTP and MCP call the same domain operations and authorization checks.

1. Authenticate caller and project; validate a typed operation and trusted
   template version against current policy. Resolve secret references outside
   model context. Reject arbitrary executable template input.
2. Produce a preview bound to exact desired revision, observed resource
   identities, policy version, dependency set, proposed cost and bounded scope.
3. Evaluate existing authority. Routine operations within a configured policy
   can proceed automatically, including production releases and recovery.
   Destructive deletion, access expansion, new spend beyond allowance and other
   exceptional changes require the applicable explicit current human grant.
   Being in production alone does not force a new approval for every retry.
4. Dispatch through the qualified protected executor with idempotency identity,
   one operation owner and fenced ownership. Preserve the external executor's
   authoritative lifecycle and keep local projections clearly identified.
5. Record authoritative provider readback and completion evidence. A timeout or
   crash after dispatch is `unknown`, not failed-and-safe-to-repeat. Reconcile
   before retry; cancellation cannot recall an already accepted mutation.
6. Have Bora or an independent evidence path verify expected operational and
   cost outcomes. An apply exit code alone does not establish live correctness.

Authorization binds caller, project/environment, exact operation or approved
policy class, artifact/preview digest, privileges, cost, expiry and attempts.
Changing the preview outside the grant requires reevaluation. Credentials must
be short-lived and scoped per account/environment/operation where supported;
never return them in tool responses, diffs, logs or prompts.

## Retirement and reconciliation

Retirement is a first-class lifecycle, not a delete command. First reconcile
resource ownership and dependencies, shared infrastructure, data retention,
backup recovery, DNS, credentials, certificates and pending operations. Produce
an exact ordered plan with expected recurring-cost changes and explicit unknowns.
Apply only authorized targets through the owning protected workflow. Preserve
required recovery artifacts and evidence; record what remains retained and
billable rather than calling it fully removed.

Completion requires authoritative resource absence or the accepted retained
state, current DNS/routing and credential disposition, recovery obligations,
and follow-up cost evidence with billing lag disclosed. Absence of traffic,
low CPU, an empty cluster or a deleted hostname alone is insufficient. Unowned
resources are flagged for disposition, not autonomously deleted. Periodic drift
reconciliation detects unexpected creations and retired-project leftovers.

## Security, governance and failure recovery

Separate untrusted request processing, read-only inventory and privileged apply
identities. Enforce project isolation at every layer, deny template/argument
injection, restrict outbound destinations and protect metadata endpoints.
Catalog templates and policy changes need independent review, versioned rollout
and rollback. `request_capability` creates a bounded design proposal; it grants
no infrastructure permission. Every template has an owner and compatibility
policy; retirement cannot silently invalidate a consumer.

Audit caller intent, exact preview, policy/grant, dispatch attempt, scoped
executor identity and provider outcome. Independent cloud-audit monitoring
flags mutations outside enrolled principals, including break-glass actions.
Break-glass access is separately granted, time-bound, logged and reconciled.
Alert delivery and recovery do not depend solely on ASSI's process being alive.
Test concurrent dispatch, lease expiry, restart, ambiguous provider responses,
revocation during execution, drift, partial apply, rollback and restored state.

## Adoption and current priorities

Use a time-boxed evidence-based comparison of existing IaC/protected CI and
custodian components before building new orchestration. Pulumi Automation API
is a candidate adapter, not permission to replace qualified existing controllers.
Begin with read-only inventory and ownership mapping, then preview-only shadow
requests, bounded controlled effects, and explicit per-scope credential cutover.
Do not remove existing working identities or claim sole custody before the
replacement passes actual consumer/provider, audit, recovery and rollback gates.

Production observability has priority: AWS, Kubernetes, Go core with other OSS
dependencies permitted, and a separate $100/month observability ceiling. The
first telemetry rollout uses an already qualified protected deployment route;
it does not wait for complete ASSI, APRL or Gist implementation. No EKS migration,
new infrastructure provisioning or expanded spending is approved by this RFC.

## Acceptance and delivery ownership

Required evidence includes a complete scoped inventory with explicit gaps;
project-owned desired footprint; typed policy denial and tenant isolation;
read-only shadow comparisons; real bounded apply/readback; ambiguous-outcome
recovery; reviewed retirement preserving shared/data dependencies; credential
cutover audit; backup/restore and operator recovery. Report implementation,
fixture checks, provider qualification and live operational acceptance separately.

All dispatchable cross-project work lives in
[Foundry's portfolio plan](https://github.com/sirerun/foundry/blob/main/docs/portfolio-plan.md).
The local [plan pointer](../plan.md) adds no second graph. Exact provider/account
scope, policy thresholds, templates, deployment identities, selected state store
and qualified executor bindings remain explicit preflight outputs. Public docs
contain no credentials or private resource inventory.
